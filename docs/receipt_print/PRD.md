## §1 범위

### 1.1 범위 안

1. ESC/POS 출력 기반 — 명령 바이트 생성, CP949 한글, 한 줄 폭 계산·줄바꿈, 시리얼 포트 송신, 상태 조회(Phase 33).
2. 납부확인증 양식 조립 + 결제창 902614 승인 시 자동 출력 + 실패 경고(Phase 34).
3. 직전거래 전표출력 버튼 실동작 + 마지막 영수증 SQLite 저장(Phase 35).
4. 800000 `#14` 카드번호 필드 확장과 영수증 카드번호 줄 연결(Phase 36, **SPEC 개정본 수령 후 착수**).

### 1.2 범위 밖

- 실제 키오스크(소켓 POS) 거래의 영수증 출력 — 키오스크가 자체 출력한다.
- 원본 MFC 전표 설정의 나머지 항목: **전표 매수**(`PRINTER_SLIP_NUM`), **전표 메시지**(`PRINTER_MSG1`~`MSG10`),
  `PRINTER_REPRINT`(운영 PRD §2.8.8에서 이미 제외). 영수증은 항상 1매.
- Windows 프린터 드라이버/스풀러, USB 직접 제어, 네트워크 프린터.
- 로고·바코드·QR 이미지 출력.
- 취소 전표(902614 취소 거래 자체가 SPEC에 없다).
- 프린터 장애의 서버 알림(장애 알림 대상 추가는 `docs/operations/fault_alert_catalog.md`에서 별도 판단).

## §2 데이터 출처

### 2.1 원칙 — 결제창 탭의 응답값을 쓴다 (사용자 확정)

원캡 중계 경로(`PaymentOrchestrator`/`PosSocketServer`/`TransactionQueue`)는 전문별로 상태를 갖지 않는다
(payment_relay PRD §13.2). 영수증에 필요한 값 중 일부는 902614에 없고 501008·800000 응답에만 있으므로,
**결제창(키오스크 역할 대행)이 이미 들고 있는 세 탭의 응답값**을 모아 영수증을 만든다. 영수증은 결제창
거래에만 출력하므로(§0) 이 방식으로 충분하다.

- 조립은 **ViewModel(결제창) 쪽 책임**이다. 원캡 중계 경로는 이 기능 때문에 바뀌지 않는다(Phase 36의
  카드번호 필드 변경은 SPEC 개정에 따른 것이지 영수증 때문이 아니다).
- 탭 값의 수명 = 결제창 탭의 수명(사용자 확정). 별도 메모리 캐시를 두지 않는다.

- **501008 탭을 1순위로 쓰는 조건(2026-09-30 확정, 같은 날 CP1 보강)**: 501008 탭에 응답이 있고, **그 응답
  `#7`이 `000`(정상 조회)**이며, `#14` 전자납부번호가 902614 `#15`와 같을 때만(두 번호 모두 비어 있지 않아야 함). 다르거나 응답이 없으면 501008 값을 전부 버리고 대체 출처/빈칸을 쓴다(다른
  고지서의 납기 정보가 섞여 찍히는 것을 막는다). 800000 탭도 응답이 있을 때만 쓴다(짝 검사 키가 없음).
- 1순위 값이 **비어 있거나 공백뿐이면 대체 출처**를 쓴다(2026-09-30 CP1 보강). 대체 출처가 없는 항목(납기 4줄)은 빈칸.

- 이 표의 필드 번호는 SPEC 20260922(재배포본) 기준이다. 800000 SPEC 개정(§2.4) 시 800000 쪽 번호·위치가
  바뀔 수 있으므로 Phase 36에서 이 표를 다시 확인한다.

### 2.3 승인 판정

**902614 응답 `#7` 응답코드가 `000`일 때만 출력한다.** 그 외(인터넷지로 응답코드 `111`~`201`, 원캡 응답코드
`E`/`R`/`D` 계열, 전송 실패·타임아웃)는 출력하지 않는다. 결제창의 "응답 수신" 배지는 응답을 받았다는 뜻일
뿐 승인이 아니므로 판정 기준으로 쓰지 않는다.

### 2.4 카드번호 — 800000 `#14` 마스킹 카드번호 (SPEC 20260930 개정 반영)

- 현재 세 전문 어디에도 카드번호를 키오스크로 돌려주는 필드가 없다. 800000 `#14`는 BIN(AN8, 카드번호
  앞 8자리, 원캡이 카드리딩으로 채움)이고, 902614 `#46`은 암호화 데이터이며 응답에서 지워진다(Phase 26).
- **결정**: 800000 `#14`를 **최대 카드번호 길이 19자리** 필드로 늘리고, 원캡은 리더기가 준 카드번호를
  그대로 넣는다. 이후 POSITION이 전부 밀리므로 **새 SPEC이 나온다**.
- 리더기 카드번호는 **이미 마스킹돼 있다**: 암호화리더기설계서 §3.39 `[3B] 거래정보 응답`(p.89) — "카드
  번호 앞자리 9~12번째 자리와 마지막 자리 … 마스킹", 마스킹 문자 `*`, 예시
  `11112222****444*D****123********12345`(reader-pinpad-spec-expert 확인, 2026-09-30). 따라서 원캡과
  영수증 모두 **별도 마스킹을 하지 않는다**.
- **SPEC 20260930 개정 결과**(pos-onecap-spec-expert 두 판 대조): `#14` `BIN`(AN8) → `마스킹 카드번호`(AN19,
  POSITION 70, 원캡 SET), `#15~#28` POSITION +11, `#28` 예비 필드 AN216→AN205(총 길이 500 유지). 원문 설명은
  "앞 8자리 BIN은 마스킹 제외(신용,체크 구분 시 사용)"뿐이다.
- **채움 규칙(SPEC에 없어 사용자 확정, 2026-09-30)**: 리더기 카드번호 필드에서 **구분자(`D`/`=`) 앞의 숫자·`*`
  부분만** 떼어, **왼쪽 정렬 + 공백 채움**(AN 관례). 19자 초과면 앞 19자. 구분자가 없으면 숫자·`*`가 이어지는
  데까지. 8자 미만이면 기존 BIN 추출 실패와 같은 방어 경로(`ReaderNoCardDataDefensiveCode`).
- **전문 로그**: 리더기 마스킹 그대로 남긴다(`TelegramLogRedactor` 변경 없음, 사용자 확정).
- 예외 거래구분(포인트 `P` 평문, RF-B CSN, EMV-QR 7~12 마스킹, QR `q` 평문)은 국세 신용카드 결제 흐름에서 쓰지
  않으므로 별도 처리를 두지 않는다(값이 오면 위 규칙 그대로 적용).
- 영수증: 800000 응답 `#14` 트림 → 4자리마다 `-`(§3.4). 800000 응답이 없으면 빈칸.

## §3 영수증 양식

### 3.1 용지·폭

- 80mm 롤, **한 줄 42칸(바이트)** 기준(Font A). 근거: 샘플의 `세입징수관서 : 국세청 서울지방국세청 강서`가
  CP949 41바이트이고 다음 글자 `세`(2바이트)가 다음 줄로 넘어가 있다 → 42칸 프린터. **2026-09-30 실기 확정.**
- 42칸 영역이 용지 왼쪽에 붙어 오른쪽만 비어 보이므로 **왼쪽 여백(`GS L` 36)으로 가운데 정렬**한다(2026-09-30
  사용자 확정, `PrinterProfile.LeftMarginDots`).
- 한글은 2칸, ASCII는 1칸으로 계산한다(CP949 바이트 수).

```
납부일자 : 2026.08.19
------------------------------------------
                                              ← 빈 줄
1.신용카드로 납부한 국세는 할부거래계약서
및 약관 등에도 불구하고 납부를 취소할 수

2.신용카드로 국세를 납부할 경우 납부세액의

```

- 항목 행은 `라벨 + " : " + 값`, 왼쪽 정렬. 값이 넘치면 다음 줄 맨 앞부터 이어 쓴다(샘플과 동일). 2바이트
  글자를 반으로 자르지 않는다. 줄바꿈으로 생긴 줄의 **끝 공백은 제거**하고 맨 앞 공백은 둔다(2026-09-30 확정).
- 제목은 2배 크기라 한 줄 21칸이다. 고정 문구 `종합소득세 납부확인증`(CP949 21바이트)이 정확히 한 줄에 들어간다.
- 샘플 맨 아래 구분선은 두 줄(`---` 두 번)로 보이나 **한 줄로 통일한다(제안)** — 샘플 사진상 윗줄은 이전
  구획의 구분선과 겹쳐 보이는 것으로 판단.

### 3.3 고정 문구 (하단 안내)

```
1.신용카드로 납부한 국세는 할부거래계약서 및 약관 등에도 불구하고 납부를 취소할 수 없습니다.
2.신용카드로 국세를 납부할 경우 납부세액의 0.8%인 납부대행수수료는 납세자가 부담합니다.
```

- 1번 문구는 고정. **2번 문구의 수수료율은 800000 응답 `#26`에서 가져온다**(2026-09-30 사용자 확정).
  - **형식: 소수점 2자리**(앞 2자리 정수부 + 뒤 2자리 소수부, 단위 %). **`0050` = 0.50% → 표시 `0.5%`**
    (2026-09-30 사용자 정정 — 처음 "소수점 3자리"로 정했다가 같은 날 `0.5% → 0050`으로 바로잡음. SPEC 원문에는
    형식 설명·예시가 없음, pos-onecap-spec-expert 확인). 표시할 때 소수부 끝의 0을 떼고, 소수부가 전부 0이면
    점도 뗀다(`0080` → `0.8%`, `0075` → `0.75%`, `0100` → `1%`).
  - **값이 없을 때**(800000 탭 응답 없음, `#26` 공백·숫자 아님): 요율 부분을 뺀 문구
    `2.신용카드로 국세를 납부할 경우 납부대행수수료는 납세자가 부담합니다.`(2026-09-30 사용자 확정).
  - 다음 SPEC 개정 때 `#26` 형식(소수점 2자리, 예 `0050`=0.5%)과 예시값을 원문에 싣는 것을 검토한다 —
    `docs/payment_relay/spec_open_questions.md`에 기록.
- 줄바꿈 위치는 §3.2 규칙(42칸)을 따른다. 요율이 `0.8%`이면 샘플과 글자 단위로 같게 나온다 — 2번 문구의
  둘째 줄 맨 앞 공백은 원래 문자열 `…납부세액의 0.8%인…`에서 42칸째에 걸린 공백이 다음 줄 맨 앞으로 넘어간
  것이다. 요율 자릿수가 다르면 줄바꿈 위치도 달라진다(정상).

### 3.4 마스킹

| 항목 | 규칙 | 근거 |
|---|---|---|
| 납세자번호 | 앞 6자리만 보이고 나머지 전부 `*`(13자리면 `800101*******`). 6자리 이하면 그대로(제안) | 샘플(사용자 확정) |
| 카드번호 | 원캡·영수증 모두 마스킹하지 않는다 — 리더기가 이미 9~12번째·마지막 자리를 `*`로 준다(§2.4). 영수증은 4자리마다 `-`만 넣는다 | 사용자 확정 |

- 영수증에 찍히는 모든 값은 이미 마스킹된 것이다. 이 원칙은 §6(재출력 저장)과 로그에도 그대로 적용된다.

## §4 출력 트리거와 흐름

### 4.1 자동 출력 (결제창 902614)

```
결제창 902614 [전송] → 원캡 중계(카드리딩·PIN·VAN) → 결제창이 응답 수신
   → 응답 #7 == "000" ?  ─ 아니오 → 끝(출력 없음)
        │ 예
   → 영수증 조립(§2.2, 세 탭 값) → 마지막 영수증 저장(§6, ON/OFF와 무관)
   → 설정 읽기(ShopSettingsService.Load(), 캐시 금지)
   → PRINTER_CHECK OFF ? ─ 예 → 끝(로그 INFO "전표 인쇄 사용 안 함")
        │ 아니오
   → 백그라운드 출력(§4.3) → 실패면 결제창에 경고창(§5)
```

- **출력은 응답 처리(연쇄 적용·배지 갱신) 뒤에 한다.** 결제창의 전송 버튼 잠금(`IsSending`)은 출력과 무관하게
  응답 수신 즉시 풀린다(**제안** — 출력 중에 다음 거래를 막을지는 §9 #4).
- 저장(§6)은 출력보다 **먼저**, 그리고 **전표 인쇄 사용 ON/OFF와 무관하게** 한다(2026-10-01 사용자 확정) — 출력이 실패했거나
  OFF로 운영하다 손님이 영수증을 찾을 때도 직전거래 전표출력으로 뽑을 수 있게.

### 4.2 직전거래 전표출력 (가맹점 설정 화면)

- 버튼을 누르면 SQLite에 저장된 마지막 영수증(§6)을 그대로 다시 출력한다. 저장된 것이 없으면 안내창
  `출력할 직전 거래가 없습니다.`(정보 아이콘, 2026-10-01 확정).
- Phase 31 규칙 유지: 버튼은 전표 인쇄 사용 ON/OFF와 무관하게 항상 활성, **포트는 화면 입력칸의 값**을 쓴다
  (저장 전 값 포함, 운영 PRD §2.8.5). 포트 입력칸이 비면 기존 오류창 `프린터 포트번호를 입력해주세요.`.
  속도도 화면 콤보의 현재 값을 쓴다(2026-10-01 확정). 포트 번호 형식이 잘못됐으면(1~255 밖 등) 출력 서비스가 `InvalidPort`로
  실패하고 §5 경고창을 띄운다. **전표 인쇄 사용 설정은 보지 않는다**(재출력은 사용자가 명시적으로 요청한 것).
- 출력 성공 시에는 별도 안내창을 띄우지 않는다(출력물 자체가 결과). 실패면 가맹점 설정 화면에 §5 경고창(재출력 안내 문구는 붙이지 않음).
- 재출력 영수증은 **제목 위에 `(재출력)` 한 줄**을 추가한다(가운데 정렬, 보통 크기 — 2026-09-30 사용자 확정).

### 4.3 출력 단계 (공통)

1. 포트 열기 — `COM{PRINTER}`, `PRINTER_SPEED` bps, 8N1, 흐름제어 없음(**Phase 33 실기 확인**).
2. 상태 조회 — `DLE EOT 2`(오프라인 원인: 커버 열림 등), `DLE EOT 4`(용지 센서). 각 응답 대기 **500ms**
   (**제안**, 실기에서 조정). 무응답이면 `프린터 응답 없음`으로 실패 처리.
3. 초기화(`ESC @`) → 본문 → 여백 → 부분 커팅.
4. 포트 닫기(`finally`에서 항상).

- 명령 바이트 근거는 `escpos_reference.md`.
- 포트 열기~닫기 전체를 백그라운드에서 수행한다. UI 스레드를 막지 않는다.
- 같은 프린터로 동시에 두 출력이 가지 않도록 출력 서비스 안에서 직렬화한다(자동 출력 중 재출력 버튼 등).

## §5 실패 처리

| 실패 | 판정 | 결제창/설정창 표시(제안 문구) | 로그 |
|---|---|---|---|
| 포트 번호 없음·잘못됨 | 설정값 비어 있음/1~255 밖 | `전표 출력 실패\n프린터 포트 설정 확인.` | WARN |
| 포트 열기 실패 | `SerialPort.Open` 예외(없는 포트, 다른 프로그램 사용 중) | `전표 출력 실패\n프린터 포트를 열 수 없습니다.` | ERROR |
| 프린터 무응답 | 상태 조회 타임아웃 | `전표 출력 실패\n프린터 응답 없음.` | ERROR |
| 용지 없음 | `DLE EOT 4` 용지 끝 비트 | `전표 출력 실패\n용지 없음.` | ERROR |
| 커버 열림 | `DLE EOT 2` 커버 비트 | `전표 출력 실패\n프린터 덮개 열림.` | ERROR |
| 쓰기 실패 | 쓰기 타임아웃/예외 | `전표 출력 실패\n전송 오류.` | ERROR |

- **표시 문구 형식**(2026-10-01·10-02 사용자 확정, 근거 `docs/alert_dialog/PRD.md` §4.2 #6·#14, §4.4): 첫 줄 `전표 출력 실패`는
  알림창 제목, 둘째 줄은 사유 문장(마침표 포함)이다. 이전 형식 `전표 출력에 실패했습니다. (사유)`는 알림창 제목 한 줄 규칙에 맞추며 바뀌었다.
- **표에 행이 없는 사유**(`PrinterError`·`CompositionFailed`·`Unexpected` 등)는 사유 줄 없이 **제목만**(`전표 출력 실패`) 표시한다(2026-10-02 사용자 확정).

- **상태 조회를 끈 기종(현재 개발 PC 프린터)에서는** 용지 없음·커버 열림·무응답 행이 발생하지 않는다 — 포트가
  열리고 송신이 끝나면 성공으로 기록된다. **프린터 전원이 꺼져 있어도 성공으로 기록됨을 실측**했다(2026-09-30 — USB-시리얼
  변환기가 PC 전원으로 데이터를 받아 버림). 이 경우 사용자는 영수증이 안 나온 것을 눈으로만 알 수 있고, 직전거래 전표출력(§4.2)으로
  다시 뽑는다.
- 경고창은 결제창(자동 출력) 또는 가맹점 설정 화면(재출력) 위에 **알림창 Warning**(`docs/alert_dialog/` — 5차 범위에서
  Windows 기본 메시지 박스를 대체)으로 띄운다. 경고창 끝에 재출력 안내 줄 `가맹점 설정에서 다시 출력하세요.`를 덧붙인다(자동 출력일
  때만 — 2026-10-01 확정, Phase 35부터. 처음 문구 `가맹점 설정의 '직전거래 전표출력'으로 다시 출력할 수 있습니다.`는 알림창 한 줄
  폭을 넘어 2026-10-01 축약, alert_dialog PRD §4.4). 예: 자동 출력 + 용지 없음 = `전표 출력 실패\n용지 없음.\n가맹점 설정에서 다시 출력하세요.`,
  자동 출력 + 행 없는 사유 = `전표 출력 실패\n가맹점 설정에서 다시 출력하세요.`
- **거래 결과는 바뀌지 않는다.** 승인은 이미 성립했다.
- 용지 **부족**(near-end)은 실패가 아니다 — 출력은 하고 WARN 로그만(제안).
- **로그 code는 `S12` 하나**(전표 출력 실패, 사유는 본문 — 2026-09-30 사용자 확정). S 계열은 POS로 나가지 않는
  로그 전용 내부 사건 코드다(운영 PRD §1.12.2). **장애 알림 대상 아님(`N`)** — S 계열 중 첫 `N`이라
  `docs/operations/fault_alert_catalog.md` §2.2에 예외로 명시한다. 로그에는 영수증 본문을 남기지 않는다(결과·사유·바이트 수만).

## §6 직전거래 저장 (SQLite, 사용자 확정)

- `IntegrityCheckStore.DefaultDatabasePath()`와 같은 SQLite 파일에 별도 테이블 `last_receipt`, **고정 키 1행
  upsert**(`LastTransactionResponseStore`와 같은 패턴, 이력 없음).
- 저장 내용은 **영수증 모델(`NationalTaxReceipt`)의 항목 값**과 저장 시각. ESC/POS 바이트가 아니라 값을 저장한다 — 양식을 고쳐도
  재출력이 새 양식으로 나오게. **단 납세자번호는 저장 전에 마스킹**(앞 6자리 + `*`)한다 — 모델에는 원문이 들어 있으므로 원문 13자리가
  디스크에 남지 않게 한다(카드번호는 리더기가 이미 마스킹한 값).
- 저장되는 개인정보: 납세자명, 앞 6자리만 남은 납세자번호, 마스킹된 카드번호, 전자납부번호. 사용자가 SQLite
  저장을 택하며 이 잔존을 수용했다(2026-09-30).
- 공개 메서드는 예외를 던지지 않는다(저장 실패는 WARN, 출력은 계속).

## §7 구현 원칙

### 7.1 계층 (payment_relay ROADMAP "계층 구조" 규칙 연장)

```
src/KFTCOneCAP.Wpf/
├─ Protocol/Printer/     ESC/POS 명령 바이트, CP949 폭 계산·줄바꿈, 상태 응답 파서 — 순수 함수, I/O 없음
├─ Services/Printer/     시리얼 포트 열기·상태 조회·송신·닫기, 직렬화, 결과 객체 반환(예외 미전파)
├─ Services/Receipt/     (제안) 납부확인증 모델 → 인쇄 문서 변환(양식 규칙), 설정 확인 후 출력 서비스 호출
├─ Services/Storage/     LastReceiptStore (SQLite)
└─ ViewModels/Payment/   세 탭 값 → 납부확인증 모델 조립(§2.2), 승인 판정(§2.3), 경고 이벤트
```

- 의존 방향 `ViewModels → Services → Protocol`. `Services`는 WPF 타입을 모른다.
- 바이트 빌더는 포트 없이 16진 덤프로 검증 가능해야 한다(진단 인자 `--receipt-print-test`).
- 영수증 모델 조립은 전문 필드 번호를 아는 유일한 곳(ViewModel)에 둔다. `Services/Receipt/`는 필드 번호를
  모르고 이름 붙은 값만 받는다.

### 7.2 기타

- `net48`/x86 유지. `System.IO.Ports`는 .NET Framework 기본 포함.
- 설정값은 매 출력 직전에 읽는다(운영 PRD §2.6). `PRINTER_CHECK`는 ON="1".
- 새 화면 코드는 MVVM(CLAUDE.md).

## §8 검증 방법

- **바이트 단위**: 진단 인자로 샘플 데이터 영수증의 16진 덤프를 찍어 기대값과 대조(포트 불필요).
- **실기**: 개발 PC에 연결된 Epson 호환 80mm 프린터로 샘플 데이터를 출력해 사진 샘플과 대조(사용자 육안).
- **실패 경로**: 용지 제거, 커버 열기, 전원 끄기(무응답), 없는 포트, 속도 불일치를 실기에서 재현.
- **결제창 E2E**: 결제창에서 501008 → 800000 → 902614를 보내 자동 출력 확인. 실 VAN 서버가 없으면 VAN 스텁의
  승인 응답(`#7=000`)으로 대체하고 그 사실을 명시한다. 앱이 `requireAdministrator`라 GUI 자동화가 UIPI에
  막히므로 화면 조작은 사용자가 하거나 기존 방식대로 `asInvoker` 일시 해제 후 원복한다.
