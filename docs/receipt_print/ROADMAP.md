# ROADMAP: 국세 납부확인증 영수증 출력 (4차 범위)

> `PRD.md`(무엇을)를 기준으로 **어떤 순서로, 어디까지 하면 끝인지**를 정의한다. Task 단위 지시·완료 조건은
> `development_plan.md`(각 Phase 착수 직전 작성)에서 다룬다.
>
> **Phase 번호는 앞 범위에서 이어진다** — 1차 0~6, 2차 7~21·26·29~30·32(`docs/payment_relay/`), 3차
> 22~25·27~28·31(`docs/operations/`). 이 범위는 **33부터**다.

## 작업 방식 (앞 범위와 동일)

1. Phase는 순서대로 진행한다. 완료 기준을 통과하지 못하면 다음으로 넘어가지 않는다.
2. 각 Phase 종료 시 `dotnet build` 성공 + 실제 실행 검증. 실기(프린터)가 필요한 항목은 **확인한 것만** 완료로
   표시하고, 못 한 것은 그 사실을 적는다.
3. PRD와 구현이 어긋나면 PRD를 먼저 고친다.
4. PRD에 없는 결정이 필요하면 즉시 사용자에게 묻는다(`PRD.md` §9 미확정 표를 먼저 갱신).
5. Opus 설계 → Sonnet 구현 → 자체 테스트 → Opus 검증 → 수정 → Opus 재확인, 체크포인트마다
   `checkpoint-reviewer`(같은 세션 서브에이전트, 중립 프롬프트).

**목표**: 영수증 데이터와 무관하게, **정해진 텍스트 문서를 실제 프린터에 원하는 모양으로 찍는 능력**을 먼저
완성한다. 결제 흐름·화면은 건드리지 않는다.

**왜 먼저인가**: 양식(Phase 34)을 맞추려면 한 줄 칸 수·한글 출력 방식·커팅·상태 조회가 실기에서 어떻게
동작하는지 알아야 한다. 이 값들이 흔들리면 양식 코드가 두 번 바뀐다.

### 작업 항목

- [x] 실기 정보 기록(모델명·연결 포트·속도·한국어 펌웨어 여부) — `escpos_reference.md` §5
- [x] `Protocol/Printer/` — 명령 바이트 상수, CP949 폭 계산·줄바꿈(`라벨 : 값` 행, 42칸, 2바이트 글자 보호),
      인쇄 문서 모델(줄 목록 + 정렬/배율) → `byte[]` 변환, `DLE EOT` 상태 응답 파서
- [x] `Services/Printer/` — 시리얼 출력 서비스(포트 열기 → 상태 조회 → 송신 → 닫기, 직렬화, 결과 객체 반환·

### 완료 기준

## Phase 37 — 결제창·VAN 스텁 테스트값 현실화 — ✅ 완료 (2026-10-01)

**추가 확정(2026-10-01)**: 수수료율 신용 0.8%/체크 0.5%, 세목 코드 종합소득세 `10` 가정. 필드별 값 표는 `development_plan.md` Phase 37.

**목표**: 결제창(kiosk 역할 대행)이 채우는 요청 임의값과 VAN 스텁이 채우는 응답 난수를, 실제와 비슷하면서 테스트임을 알 수 있는
값으로 바꾼다. 영수증 실기(Phase 34)에서 납세자명·징수기관명·날짜·수수료율이 무의미한 문자열로 찍힌 것이 계기.

**확정 사항(2026-10-01)**: ① 범위 = 결제창 요청값 + VAN 스텁 응답값 둘 다(연쇄로 섞이므로) ② 이름류는 "테스트" 표시(예: 납세자명
`테스트납세자`, 징수기관 `테스트세무서 징수관`), 금액·날짜·번호는 현실적 범위에서 거래마다 변동(납기일은 오늘 이후, 본세+농특세+교육세
=납부세액, 수수료=세액×요율, 합계 일치), 카드사명은 SPEC 20260930 p.14 카드사 코드표 ③ Phase 34 실기 이후 진행.

**착수 전 확인**: 필드별 표현·길이·SET 장소는 `pos-onecap-spec-expert`로, 결제창 난수 생성(`PosRandomValueGenerator`, Phase 29)과
스텁 채움(`StubVanRelayService`, P30-1)의 기존 규칙·테스트를 읽고 실행계획서를 쓴다. 실 VAN 연동 시 스텁 자체가 빠진다는 점(P30-1)은 그대로.
