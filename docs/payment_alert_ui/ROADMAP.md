# ROADMAP: 결제 알림창 UI/UX 개선 (6차 범위)

> `PRD.md`(무엇을)를 기준으로 **어떤 순서로, 어디까지 하면 끝인지**를 정의한다. Task 단위 지시·완료 조건은
> `development_plan.md`(각 Phase 착수 직전 작성)에서 다룬다.
>
> **Phase 번호는 앞 범위에서 이어진다** — 1차 0~6, 2차 7~21·26·29~30·32·40(`docs/payment_relay/`), 3차
> 22~25·27~28·31(`docs/operations/`), 4차 33~37(`docs/receipt_print/`), 5차 38~39(`docs/alert_dialog/`).
> 이 범위는 **41부터**다.

## 작업 방식 (앞 범위와 동일)

1. Phase는 순서대로. 완료 기준을 통과하지 못하면 다음으로 넘어가지 않는다.
2. 각 Phase 종료 시 `dotnet build` 성공 + 실제 실행 캡처. 확인한 것만 완료로 표시하고 못 한 것은 그 사실을 적는다.
3. PRD와 구현이 어긋나면 PRD를 먼저 고친다. PRD에 없는 결정은 즉시 사용자에게 묻는다(§6 미확정 표 먼저 갱신).
4. 모델 선택은 Task 성격으로 — 시각 품질·디자인 판단은 Opus, 명세로 완결되는 로직은 Sonnet, 기계적 치환은 Haiku
   (`development_plan.md` Task 표에 근거 기록).
5. Task 사이클: 구현 → 자체 테스트 → 검증(diff 직접 읽기 + 핵심 명령 재실행) → 수정 → 재확인. 체크포인트는
   `checkpoint-reviewer`(중립 프롬프트).
6. **항상 `main`에서 작업**, push 전 확인. 앱이 떠 있는 프로세스는 누구 세션인지 확인 전에 종료하지 않는다.
   GUI 자동화는 `__COMPAT_LAYER=RunAsInvoker`로 띄워 UIPI를 피한다(manifest 수정 없음).

## Phase 41 — 창 윤곽 + 공통 프레임 (PRD §2.1, §2.3)

**목표**: 어떤 배경 위에서도 결제 알림창의 경계가 보인다. 이후 Phase의 바탕이 되는 프레임을 먼저 확정한다.

**왜 먼저인가**: 그림자 여백(40)이 창 크기·위치·Viewbox 스케일에 영향을 주므로, 내부 문구·PIN 화면을 만지기 전에
프레임 치수를 확정해야 다시 손대지 않는다. 사용자가 가장 먼저 지적한 문제이기도 하다.

**착수 조건**: PRD §6 #1·#3·#5 확정.

### 작업 항목
- [ ] 현재 화면 "전" 캡처 보관(`docs/payment_alert_ui/screenshots/before_*.png` — 카드 요청 IC·MS, 거래중, PIN)
- [ ] `AllowsTransparency` 전환 + 카드(흰 배경·1px 테두리·반지름 16·그림자) + 투명 여백 40, Viewbox를 카드 안으로
- [ ] 창 위치: 카드(여백 제외)가 화면 중앙에 오도록 보정(홈 화면 활성화 방지·Owner 미지정 유지)
- [ ] 취소 버튼 보조 버튼 스타일 정리(로직 불변)
- [ ] 글자 렌더링(`ClearTypeHint`) 확인 — 투명 창에서 글자 흐림 없는지
- [ ] 밝은/어두운 바탕·결제창 위 캡처로 윤곽 확인

### 완료 기준
- 흰 화면·어두운 화면·결제창 위 세 경우에서 윤곽이 구분됨(캡처 + 사용자 확인).
- 일반·컴팩트 모드에서 카드가 화면 중앙, 그림자 잘림 없음.
- `--payment-flow-test`·`--presenter-test` 통과, `--notice-van-processing-test`에서 VanProcessing 중 ESC 무시 유지.
- `PaymentNoticeViewModel` diff 없음(취소 게이팅 불변).
